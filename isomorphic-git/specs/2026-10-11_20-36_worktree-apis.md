## Findings before code
- checkout(filepaths)传ref+force:true，但没有noUpdateHead；vendor默认ref提供时noUpdateHead=false，可能把HEAD切换到restore来源。它也会改index，不等于只还原工作区。
- restore同样checkout HEAD force，可能抹掉staged内容；生产fs.lstat ENOENT可能throw但旧代码把不存在当null，丢文件恢复失败。文件路径checkout没有与restore相同path containment校验。
- vendor stash.apply不是三方merge：仅比较stash旧父与stashtree，直接rm/write操作，不检查当前HEAD/dirty，可能覆盖后来提交内容。pop在apply后drop，没有多文件rollback。push先write refs/stash再reflog再forcecheckout，不保证部分写可恢复。

## This step contract / changes
1. checkout(filepath)+restore共用一个regular-file worktree-only恢复helper。验证path/父链/targetlstat，不支持symlink/executable/directories；index必须tracked，source ref必须commit中存在regular100644。读blob写之前核验大小<=16MiB，singlebyte预算；直接write不先unlink。HEAD和index字节不改（含staged内容）；缺失工作区文件可恢复。明确恢复会覆盖所选worktree未提交内容，此为用户命令语义，不auto-stash；失败可能partial目标，不提供事务恢复假保证。
2. 全分支checkout保持vendor非force行为但先流式refresh:false clean check，dirty/untracked拒绝（行为收紧），pending/lock复用production dispatcher。规模/entry预算5000拒绝；未承诺跨全仓库事务原子性。
3. stash op/refIdx严格白名单与safeInteger，apply/pop前要求clean工作区/index，stash源第一父必须等于currentHEAD，拒绝advancedHEAD/dirty而不冒称支持merge。目标paths/basic modes与遍历限制后才能调用vendor。push/pop仍未等同revert事务，部分写材料与上限属于后续阶段；不把本轮通过当全stash安全闭环。
